# AI 공지 도우미 (데스크톱, 로컬 AI) — 설계 문서

- 작성일: 2026-07-15
- 상태: 설계 승인 대기 → 확정 후 구현 계획(writing-plans)으로 전환
- 원본 기획: "AI Teams Announcement Assistant" 기획서 (Teams App 전제)에서 **데스크톱 앱 + 로컬 AI**로 방향 전환

---

## 1. 요약

Teams 등에서 복사한 메시지를 입력받아, 로컬에서 동작하는 소형 AI 모델(Gemma 4 E4B)로 **회사 공지 양식에 맞는 공지문**을 자동 생성하는 **크로스플랫폼 데스크톱 앱**.

핵심 가치: 원본 메시지 → 공지 유형/언어/추가 요구사항 선택 → AI 공지 생성 → 확인·수정 → 복사.

**전 과정 오프라인.** 사내 메시지가 PC 밖으로 나가지 않는다.

## 2. 원본 기획 대비 변경 결정 (근거)

| 항목 | 원본 기획 | 이 설계 | 이유 |
|---|---|---|---|
| 전달 형태 | Teams App (메시지 `...` 메뉴 액션) | **데스크톱 설치형 앱** (Mac/Win) | Teams 메시지 액션은 Azure Bot 등록 + 앱스토어 심사 + 관리자 승인 필요. 인프라 미보유 상태에서 진입 장벽이 큼. 데스크톱은 설치파일 배포로 끝. |
| 메시지 수집 | Teams가 선택 메시지 전달 | **클립보드 감시 → 히스토리 리스트에서 선택** | `...` 메뉴 대체. 복붙 동작 없이 "복사하면 앱에 뜸". 인프라 0. |
| AI | OpenAI API | **로컬 Gemma 4 E4B** (provider 교체 가능) | 키·비용 0, 프라이버시(원문 외부 미전송), 오프라인. Apache 2.0 라이선스라 사내 배포 자유. 나중에 OpenAI/Azure로 교체 가능하도록 추상화. |
| 프론트/백엔드 | Vue3+TS+Vite / NestJS | **Tauri 2 + Vue 3 + TS** (백엔드 별도 없음) | 최종 사용자에게 가벼움 최우선(Electron ~150MB vs Tauri ~10MB). Rust core가 백엔드 역할. NestJS 불필요. |

> 참고: AI 생성 속도는 프레임워크와 무관하다. 추론은 llama.cpp(C++)가 담당하며, 껍데기(Tauri/Electron)는 설치 크기·메모리·기동 속도에만 영향.

## 3. 기술 스택

- **앱 셸**: Tauri 2 (Rust core + OS 웹뷰)
- **UI**: Vue 3 + TypeScript + Vite
- **AI 런타임**: llama.cpp `llama-server` (OpenAI 호환 REST) — Tauri **사이드카**로 구동
- **모델**: Gemma 4 **E4B**, GGUF **Q4_K_M**(또는 QAT Q4). 약 4GB, RAM 5GB 구동. 140+ 언어 지원(언어 선택 기능과 정합)
- **로컬 저장**: 앱 데이터 디렉토리에 JSON(또는 경량 SQLite) — 최근 기록/설정
- **패키징**: Mac `.dmg`, Windows `.msi`/`.exe`

### 3.1 배포/기동 전략 (JIT 다운로드)

설치파일을 가볍게 유지하기 위해 모델·런타임은 **첫 실행 시 다운로드**:

1. 설치파일(~10MB)만 배포
2. 첫 실행 시 앱이 데이터 디렉토리를 확인해 없으면:
   - OS/아키텍처에 맞는 `llama-server` 바이너리(~15MB)를 llama.cpp 릴리스에서 받음
   - Gemma 4 E4B Q4_K_M GGUF(~4GB)를 받음 (진행률 표시)
3. 이후 실행은 캐시된 바이너리·모델을 그대로 사용

> 대안(추후 선택): 사내망 배포용으로 모델을 사내 파일서버/번들에서 받도록 소스 URL을 설정 가능하게 둔다. (구현 시 옵션)

## 4. 아키텍처 & 모듈 경계

```
┌───────────────────────────── Tauri App ─────────────────────────────┐
│                                                                      │
│  Vue 3 (렌더러 / UI)                                                 │
│   - 클립보드 리스트 화면, 생성 폼, 결과/수정 화면                    │
│   - Tauri command(invoke)로 core 호출                                │
│                                                                      │
│  Rust core (백엔드 역할)                                             │
│   - clipboard watcher: 폴링 감시 → 새 항목 이벤트로 UI에 push        │
│   - ai provider: LocalProvider(사이드카 호출) [ / OpenAI / Azure ]    │
│   - runtime manager: llama-server 기동/헬스체크/종료, 모델 준비      │
│   - store: 최근 기록/설정 로컬 저장                                  │
│   - logger: 생성 로그(시간/유형/성공/응답시간, 원문 제외)           │
│                                                                      │
│  llama-server (사이드카 프로세스)  ← localhost REST(OpenAI 호환)      │
└──────────────────────────────────────────────────────────────────────┘
```

모듈은 각각 **단일 책임 + 명확한 인터페이스**로 분리한다.

- **clipboard watcher**: "무엇" = 클립보드 변화를 감지해 항목 리스트를 관리. "의존" = OS 클립보드. on/off 토글, 최근 N개 유지.
- **ai provider (인터페이스)**: `generate(prompt) -> text`, `refine(prev, instruction) -> text`. 구현체는 Local(기본)/OpenAI/Azure. UI·나머지 core는 인터페이스만 안다.
- **runtime manager**: 사이드카 수명주기와 모델 준비만 책임. provider가 이걸 통해 로컬 엔진 상태를 보장. **온디맨드 원칙**(§8.1): 앱 기동만으로는 모델을 띄우지 않고, 생성 요청 시 지연 시작, 유휴 타임아웃 후 자동 종료해 RAM을 점유하지 않는다.
- **store**: 최근 기록·설정 CRUD. 다른 모듈은 저장 포맷을 모른다.

## 5. 데이터 플로우

```
[클립보드 복사] → watcher 감지 → UI "복사한 메시지" 리스트에 추가
                                        │ (사용자 선택)
                                        ▼
[메인 폼] 원본 메시지 + 공지 유형 + 언어 + 추가 요구사항 → [공지 생성]
                                        │ invoke("generate", payload)
                                        ▼
Rust: 프롬프트 조립(System+User) → ai provider.generate → llama-server
                                        │ 결과 텍스트
                                        ▼
[결과 화면] 미리보기(수정 가능) + [다시 생성] [AI 수정] [복사]
   - AI 수정: 지시문 입력 → provider.refine(현재본, 지시) → 갱신
   - 복사: 클립보드에 결과 전체 복사
   - 기록: 생성 성공 시 store에 저장(원문 제외)
```

## 6. 화면 구성

### 6.1 메인
- **복사한 메시지 리스트**(선택): 각 항목에 미리보기 텍스트, (가능 시) 작성자/시간. 감시 on/off 토글, 전체 지우기.
- **공지 유형**(드롭다운): 일반 / 배포 / 장애 / 점검 / 회의 / 긴급 / 기타
- **언어**(드롭다운): 한국어 / English / 日本語 / 中文 / … (선택 언어로만 출력 강제)
- **추가 요구사항**(자유 입력): 예) "존댓말", "3줄 이내", "영향 범위 강조", "담당자 마지막"
- **[공지 생성]** 버튼

### 6.2 결과
- 생성된 공지 **미리보기(인라인 수정 가능)**
- 하단 액션: **[다시 생성]** / **[AI 수정]**(지시문 입력) / **[복사]**
- 생성 중 로딩 표시, 취소 가능

### 6.3 설정(최소)
- 감시 on/off, 최근 기록 개수, 모델 상태/재다운로드, (추후) AI provider 선택

### 6.4 창/트레이 동작 (트레이 최소화)
- **닫기(X)**: 앱을 종료하지 않고 **트레이로 최소화**(창 숨김). `CloseRequested` 이벤트를 가로채 종료 대신 hide 처리.
- **트레이 아이콘**: Mac은 상단 메뉴바, Windows는 시스템 트레이에 상주.
  - **좌클릭**(또는 아이콘 클릭): 창 다시 표시/포커스.
  - **우클릭 → 메뉴**: "열기", "종료". **"종료"로만 앱을 실제로 완전 종료**(사이드카도 함께 종료).
- 트레이 상주 중에도 모델은 올라가 있지 않음(§8.1) → **유휴 시 메모리 점유 최소(클립보드 감시만)**.
- (선택) 트레이 메뉴에 "감시 on/off", "모델 지금 내리기" 빠른 토글 노출 가능.

## 8. 비기능 요구사항

### 8.1 모델 온디맨드 수명주기 (메모리 절약, 필수)
모델은 **변환(생성)할 때만** 메모리에 올라간다. 앱을 켜둔 상태만으로는 RAM을 점유하지 않는다.

- **지연 시작(lazy start)**: 최초 "공지 생성"/"AI 수정" 시점에 `llama-server` 기동 + 모델 로드.
- **유휴 재사용**: 유휴 타임아웃(기본 5분) 내 재요청은 떠 있는 프로세스를 재사용(빠름).
- **자동 종료**: 유휴 타임아웃 경과 시 `llama-server` 종료 → RAM 즉시 해제.
- **명시적 종료**: 앱 종료 시 사이드카도 반드시 종료(좀비 프로세스 방지). 설정에서 "지금 모델 내리기" 수동 버튼 제공.
- **상태 표시**: UI에 모델 상태(내려감/로딩중/대기중) 표시. 첫 생성 시 로딩 시간이 붙을 수 있음을 안내.
- 타임아웃 값은 설정에서 조정 가능(0 = 매번 종료).

- **NFR-001 응답속도**: 공지 생성 10초 이내 목표. E4B Q4_K_M는 일반 노트북에서 짧은 출력 수 초 내. 단, **콜드 스타트(모델 최초 로드)** 시에는 로딩 시간이 추가되므로 로딩 상태를 명확히 표시한다.
- **NFR-002 안정성**: AI/사이드카 실패 시 명확한 에러 + **재시도** 버튼. 모델 미준비 시 준비 플로우로 유도.
- **NFR-003 보안**: 기본 오프라인, 원문 외부 미전송. (원격 provider 사용 시에만 네트워크 발생)
- **NFR-004 로그**: 로컬에만 생성 시간·공지 유형·성공 여부·응답 시간 저장. **원본 메시지는 저장하지 않음.**

## 10. 리스크 & 확인 필요

- **클립보드 실측**: Teams 복사 시 실제 담기는 텍스트/HTML(작성자·시간 포함 여부)은 구현 초기에 실측해 파싱 가능성 확정.
- **모델 다운로드 UX**: 최초 4GB 다운로드 부담 → 진행률/재개, (사내) 대체 소스 URL 옵션 고려.
- **한국어 품질**: E4B는 소형 모델. "요약+양식화" 작업엔 충분하나, 프롬프트를 양식으로 강하게 잡아 품질 안정화. 부족 시 상위 사이즈(12B) 또는 원격 provider로 스위치 가능.
- **정확한 모델/런타임 태그**: 구현 착수 시 unsloth/Google 공식 GGUF 태그와 `llama-server` 릴리스 자산명을 최종 확정.
